# IAM-001 — Least-Privilege Role Selection and Scope

| Field | Assessment |
|---|---|
| Type | Azure RBAC configuration review |
| Status | Role assignment and definitions verified; no authenticated enforcement test |
| Principal | `id-iam-reader-lab` (user-assigned managed identity) |
| Scope | `rg-iam-security-lab` |
| Assigned role | Reader |
| Compared role | Contributor (not assigned) |

## Objective

Evaluate which Azure RBAC role is appropriate for a service identity that needs to inspect resource configurations but should not change resources.

## Findings

The managed identity was assigned **Reader** directly to the lab resource group, and the Azure Portal's **Check access** view showed a single current Reader assignment with scope **This resource**.

The built-in Reader definition contained:

```json
{
  "actions": ["*/read"],
  "notActions": [],
  "dataActions": [],
  "notDataActions": []
}
```

The built-in Contributor definition contained `actions: ["*"]`, with exclusions that included `Microsoft.Authorization/*/Write` and `Microsoft.Authorization/*/Delete`. Contributor was **not** assigned to the test identity.

## Security analysis

Contributor's resource-management capabilities would be unnecessary for a read-only service identity and would increase the potential impact of misuse or compromise. Reader better follows least privilege for this scenario, while the resource-group scope avoids unnecessarily broad subscription-wide access.

This is a **preventative role-design assessment**. No existing overprivileged identity or production misconfiguration was discovered.

`notActions` is not a deny assignment. An identity may receive additional permissions through other role assignments. Role definitions must be interpreted together with scope, inheritance, deny assignments, and relevant conditions.

## Verification

**Observed:** Reader role assignment displayed in Azure Portal; scope displayed as **This resource**; Reader and Contributor definitions reviewed.

**Not performed:** Requesting a managed-identity token, making an authenticated management-plane read, or attempting a management-plane write and observing authorization failure. No enforcement-test outcome is claimed.

## Recommended next steps

1. Use the narrowest practical RBAC role and scope.
2. Review inherited and additional assignments before making effective-access claims.
3. Perform a controlled authenticated read/write test through an approved supported workload if needed.
4. Remove unnecessary assignments and lab resources at the end of the exercise.
